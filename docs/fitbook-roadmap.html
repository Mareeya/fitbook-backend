FitBook · data model roadmap

FitBook Schema Roadmap

What the six tables need to become to support attendance, a staff dashboard, and the features after that — expressed as migrations, in the order they should land. Services and controllers come later; this is the shape they'll be written against.

Written for: you, working solo on this repo.

What today's schema can't do yet

Four structural gaps, all cheap to close now and progressively more expensive once real rows exist.

NO SIGNAL

A booking has no outcome. Bookings.StatusId tracks whether the booking exists (Confirmed / Cancelled), not whether the person turned up. Nothing in the schema can distinguish a member who trained from one who ghosted — so no attendance metric is derivable from it at all.

NO COUNTERS

Occupancy is only derivable by counting. "Is this session full" means COUNT(*) over Bookings every time, and it can't be checked atomically — two members claiming the last seat will both succeed. Sessions.Capacity exists but nothing holds the number taken.

NO INDEX

Every dashboard query is a date range over Sessions.StartAt, which is unindexed. Fine at a few hundred rows, a table scan per tile at scale.

NO HISTORY

Deletes are hard deletes, and every FK is Restrict. So deleting a class that ever ran will start throwing once data exists — and if you work around that by deleting the sessions first, you erase the history the dashboard reports on. The schema needs a soft-delete concept before it needs any reporting.

Migration order

Six migrations. The first three are everything attendance and the dashboard need; the rest are the features after.

M1

Attendance on bookingsyour ask

Attendance is an outcome of a booking, so it belongs on the booking row. The unique (SessionId, UserId) index already guarantees exactly one per member per session — a separate table would have to re-establish that rule by hand and pay a join on every read.

Bookings + AttendanceStatusId int FK → Lookups -- attendance-status + SourceId int FK → Lookups -- booking-source + CheckedInAt datetime2 null + MarkedByUserId int FK → Users, null + CancelledAt datetime2 null Lookups -- seed two new types + attendance-status : Booked · Attended · NoShow · LateCancel + booking-source : Online · WalkIn · StaffBooked
  • Two status columns, not one. StatusId stays the booking's own lifecycle; AttendanceStatusId is what happened on the day. Collapsing them into one column loses the ability to say "cancelled in time" versus "cancelled an hour before".
  • SourceId is what makes walk-ins ordinary. Someone who turns up unbooked gets a booking row created at the door with WalkIn — attendance stays 1:1 with bookings, and walk-ins land in every stat automatically instead of needing their own table and their own query path.
  • MarkedByUserId nullable on purpose. Null means the automated sweep set it rather than a person — which is itself the signal that nobody closed the session out.
  • CancelledAt earns its place because LateCancel is defined relative to Sessions.StartAt. Without the timestamp you can classify it once and never re-derive it if the policy window changes.
M2

Counters and indexesenables the dashboard

Two denormalized integers turn the dashboard from an aggregation problem into a single indexed read — and fix the last-seat race at the same time. Same migration, because they're the same idea.

Sessions + SeatsTaken int not null default 0 + CheckedInCount int not null default 0 -- indexes + IX_Sessions_StartAt (StartAt) + IX_Sessions_ClassId_StartAt (ClassId, StartAt) + IX_Bookings_SessionId_Attendance (SessionId, AttendanceStatusId) + IX_Bookings_UserId_CreatedAt (UserId, CreatedAt)
  • The counters are how you claim a seat safely. UPDATE Sessions SET SeatsTaken = SeatsTaken + 1 WHERE Id = @id AND SeatsTaken < Capacity — zero rows affected means full. One statement, correct under concurrency, no read-then-write gap. Worth deciding at schema time because it's the reason the column exists.
  • Denormalized means it can drift, so plan for a reconciliation query that recomputes both from Bookings. Run it nightly or on demand; you'll want it the first time a bug leaves a counter wrong.
  • IX_Bookings_UserId_CreatedAt is for the member-facing history and the at-risk list, which query by person rather than by session.
  • Consider a filtered index on Sessions(StartAt) WHERE StatusId = Scheduled once cancelled sessions accumulate.
M3

Staff role, soft delete, auth hooksyour ask

The role change is two lines with one trap. Soft delete rides along because both touch every table's read path — and since this migration already opens Users, it's the cheapest moment to add the two columns auth will want.

UserRole enum + Staff = 4 -- append; do NOT renumber 1-3 Users · Trainers · Classes + IsActive bit not null default 1 + DeletedAt datetime2 null Users -- auth hooks; not required, but free now + SecurityStamp uniqueidentifier null + LastLoginAt datetime2 null
  • JWT itself needs no schema at all. Users already carries everything the token claims need — Id, Role, Name, Email. A stateless token is signed, not stored. Auth is a config and middleware change, not a migration.
  • What a long-lived token costs you is revocation. Promote a member to Staff and their existing token still claims Member until it expires — a role change that silently doesn't take effect, on the role that gates the dashboard. Same for a password change or someone leaving.
  • SecurityStamp is the hook that fixes that later. Rotate it on password or role change, carry it as a claim, and validate it when you're ready to pay a lookup per request. Adding the column now is free; adding it once there are users means a migration plus a backfill plus a change to the issuance path.
  • Refresh tokens are the real schema work, and they're deferred. When they land: a RefreshTokens table (UserId, TokenHash, ExpiresAt, RevokedAt, ReplacedByTokenId). Password reset wants the same table — plan them as one piece of work, not two.
  • Append the enum value, never renumber. There's already a ReorderUserRoles migration in your history — rows in the database carry those numbers. Changing an enum's numbering is a data migration with an UPDATE, not a code edit, and the two are easy to confuse.
  • Soft delete via an EF global query filter (HasQueryFilter(x => x.IsActive)) so every read excludes deleted rows without touching call sites. Sessions and Bookings keep hard rows — they're the history.
  • Watch the unique indexes. Classes.Name and Users.Email are unique; a soft-deleted row keeps occupying that name forever. Either make them filtered unique indexes (WHERE IsActive = 1) or accept that names are never reusable. This is the detail that bites later.
  • One role per user is now a known limit. A trainer who also covers the front desk can't be represented. Fine today; when a fifth role or a dual role appears, that's the trigger to move to a UserRoles join table rather than widening the enum again.
M4

Waitlistnext

The highest-value addition after attendance, and it reuses M2's counter pattern exactly — a cancellation promotes the next person and the seat never goes to waste.

Waitlist -- new table Id int PK SessionId int FK → Sessions UserId int FK → Users Position int StatusId int FK → Lookups -- Waiting · Promoted · Expired PromotedAt datetime2 null CreatedAt / UpdatedAt UK (SessionId, UserId) -- mirrors the Bookings rule
  • Separate table, not a booking status. A waitlist entry isn't a seat — folding it into Bookings would corrupt SeatsTaken and every fill-rate number that reads from it.
  • Position stored rather than derived from CreatedAt, so staff can move someone up manually.
  • Promotion is one transaction: insert the Booking, increment SeatsTaken, mark the waitlist row Promoted.
M5

Memberships and creditsrevenue model

Where the product stops being a schedule and starts being a business. Also the reason late-cancel tracking in M1 matters — a late cancel burns a credit.

MembershipPlans UserMemberships Id int PK Id int PK Name nvarchar(80) UserId int FK → Users CreditCount int null PlanId int FK → MembershipPlans IsUnlimited bit CreditsLeft int null DurationDays int StartsAt / EndsAt datetime2 Price decimal(10,2) StatusId int FK → Lookups IsActive bit CreatedAt / UpdatedAt Bookings + UserMembershipId int FK null -- which pass paid for this seat
  • Money as decimal(10,2), never float. Worth stating because EF will happily map a double and you won't notice until totals are off by fractions of a rupee.
  • CreditsLeft is a counter with the same concurrency shape as SeatsTaken — decrement conditionally (WHERE CreditsLeft > 0), same pattern, same transaction as the booking.
  • The FK from Bookings back to the membership is what lets you refund the right pass on cancellation, and what makes "revenue per class" answerable later.
  • A ledger table (one row per credit movement) is the fuller answer and the one you'll eventually want — but only once someone disputes a balance. Start with the counter.
M6

Locations and schedule templatesonly if needed

Both are cheap now and painful later. Add the location key speculatively; add templates only when creating sessions one at a time actually annoys you.

Locations ScheduleTemplates Id int PK Id int PK Name nvarchar(120) ClassId int FK → Classes TimeZoneId nvarchar(60) DayOfWeek tinyint IsActive bit StartTime time TrainerId int FK → Trainers Classes · Sessions Capacity int + LocationId int FK IsActive bit
  • The tenant key is the expensive retrofit. Adding LocationId to two tables with one seeded row costs nothing today; adding it across a populated schema means backfilling every row and revisiting every query and index.
  • TimeZoneId lives on the location because that's what actually determines wall-clock time. See the UTC decision below — this is where the answer is stored.
  • Templates generate Sessions; they don't replace them. Generated rows stay ordinary sessions so nothing downstream needs to know templates exist.

Metric → column

Each number worth putting on the dashboard, and the schema it depends on. A metric with no column behind it is a metric you can't ship.

Attendance rateattended ÷ booked

The single most useful number in the product, and completely underivable today. Always rendered against the prior period — the level alone tells you nothing. needs · M1 AttendanceStatusId

No-show rateby class and by trainer

Only trustworthy if something closes sessions out automatically. A sweep flips stale Booked rows to NoShow after the session ends — without it this counts sessions nobody marked, and every derived number is wrong. needs · M1 + a scheduled sweep

Seat utilizationtaken ÷ capacity

Reads straight off the session row once the counter exists — no aggregation, no join. This is the payoff for denormalizing. needs · M2 SeatsTaken

Active members≥1 attendance in 28 days

A retention proxy that needs no payment data. Counting registered users flatters you; counting people who showed up doesn't. needs · M1 + IX_Bookings_UserId_CreatedAt

At-risk listnamed members, not a count

Attended 4+ times last month, nothing in 14 days. The one panel someone can act on today — it produces a call list. Depends on history surviving, which is why soft delete precedes it. needs · M1 + M3 soft delete

Booking lead timemedian hours ahead

How far in advance to publish the timetable. Falls out of Bookings.CreatedAt minus Sessions.StartAt — already derivable, no new column. needs · nothing new

Waitlist conversionpromoted ÷ waiting

Whether the waitlist actually recovers cancelled seats, and therefore whether it was worth building. needs · M4

Decisions worth making before M1

Four forks that are free today and structural later. Recommendations attached.

Attendance on the booking, or its own table?

A separate Attendance table buys repeated check-in events and a fuller audit trail. It costs a join on every dashboard query plus re-establishing by hand the uniqueness rule Bookings already enforces.

Recommendation: columns on Bookings, as in M1. Split it out only if you ever need more than one check-in event per booking.

UTC or local time in StartAt?

It's a bare datetime2 with no zone today. A gym runs on wall-clock time — "the 7am class" stays 7am across a DST change, which a stored UTC instant will not.

Recommendation: store UTC, keep an IANA zone id (config now, Locations.TimeZoneId at M6), convert at the edges. Settle it before real bookings exist — it's miserable to unpick after.

Keep stretching the Lookups table?

M1 adds two more vocabularies to a table already serving three, and nothing at the database level stops AttendanceStatusId pointing at a class row. Every status join is also an extra join.

Recommendation: keep Lookups for anything a human might add (class categories), and use C# enums with HasConversion<byte> for closed sets the code branches on — attendance status, booking source. Fewer joins, and the compiler enforces what the FK can't.

One gym, or several?

Multi-location means a key on classes and sessions and a filter on essentially every query and index.

Recommendation: if a second branch is even plausible, add LocationId now with one seeded row. Retrofitting a tenant key across a populated schema is a weekend you won't enjoy.

Schema hygiene worth folding in

Small things that get harder the more tables exist. Cheap to do alongside the migrations above.

Modelling

  • Timestamps in SaveChangesSet by hand in every service today — one override means they can't be forgotten on a new entity.AppDbContext.SaveChangesAsync
  • CreatedBy / UpdatedByAdd alongside the timestamps once there's an authenticated caller to attribute.all tables
  • Trainers.Name duplicates Users.NameTwo sources of truth that can drift. Drop the column and read through the FK.Domain/Trainer.cs
  • Check constraintsCapacity > 0, SeatsTaken <= Capacity, Price >= 0. The database should refuse states the code considers impossible.
  • Rowversion on SessionsIf you'd rather have optimistic concurrency than the conditional-update pattern — pick one, not both.

Growth

  • Nightly rollup tableDailyClassStats(Date, ClassId, Booked, Attended, NoShow, CapacityOffered). Build it when the summary query crosses ~300ms — not before.
  • Notifications tableType, recipient, payload, SentAt, status. Needed the moment reminders exist, and reminders are what actually reduce no-shows.
  • PaymentsOnly after M5 memberships. A payment references a membership, not a booking.
  • Archive old sessionsNothing to do for years — but it's why Sessions and Bookings stay hard rows while everything else goes soft-delete.
  • Seed a realistic history~8 weeks of backdated sessions, bookings and attendance behind the existing Seed:Enabled flag. An empty dashboard can't be evaluated, or demoed.

Part two — controllers and endpoints

The API surface the schema above implies. Four controllers exist and need changes; five are new. Roles in the right column assume Staff = 4 from M3.

LANDED

JWT authentication is in as of 2026-09-20. Login and register issue a signed token, UseAuthentication() sits correctly before UseAuthorization(), all four controllers carry [Authorize] with [AllowAnonymous] scoped to auth, and register hard-codes the Member role so nobody can self-promote. The role claim is emitted as the enum name, so [Authorize(Roles = "Staff")] will work unchanged once M3 adds it.

KEY

The signing key is committed to appsettings.json. Anyone who can read the repo can mint a token with any user id and any role, which the [Authorize] attributes cannot detect. The project already has UserSecretsId set and appsettings.Local.json gitignored — the key simply went into the wrong file. Move it, and treat the committed one as burned.

ROLES

[Authorize] with no role means any logged-in user. A member who registers through the public endpoint can still POST /api/classes and DELETE /api/trainers/3. Anonymous access is closed; privilege escalation isn't. The role column below is what's still missing, not what's enforced.

Conventions worth fixing once

Decisions that apply across every controller. Cheaper to settle before there are nine of them.

Authorization

  • Default-denyA fallback policy requiring an authenticated user, with [AllowAnonymous] on login and register only. Opting each endpoint in means the one you forget is the one that leaks.Program.cs
  • Identity from claims, never the bodyEspecially on booking and cancellation. A userId in a request body is a request to act as someone else.
  • Ownership checks are not role checks"Member" can cancel their booking. The role gets them to the endpoint; the row check decides the rest.
  • Trainer scoping in the serviceNot via a query parameter the caller supplies.

Shape

  • Bulk over chattyAttendance marks a roster; the dashboard returns one payload. Both are cases where the obvious per-item design is the wrong one.
  • Paged envelope on every list{ items, page, pageSize, total }. Adding it later is a breaking change for every client.
  • Drop the "NotFound" stringDeleteAsync returning a magic string is spreading across services. AppException plus the existing ProblemDetails handler already does this properly.Services/*.cs
  • 409 for a full sessionNot 400. The request was valid; the world changed.
  • Idempotency on bookingA double-tapped button shouldn't need the unique index to be the thing that saves you — though it will.
